# tools/codegen

Generators for the modules of `glam` that glam-rs itself generates from one template.

## intvec.py - IVec2/3/4 and UVec2/3/4

```
tools/codegen/intvec.py            # regenerate, then `scarb fmt` the workspace
tools/codegen/intvec.py --check    # exit 1 if a committed file differs from the generator output
tools/codegen/intvec.py --only src,tests,bench,alt
```

Dependency-free (python >= 3.8, `scarb` on the `PATH` for the formatting pass). For each of the
six types it writes four files, all starting with `// GENERATED by tools/codegen/intvec.py`:

| output | template |
|---|---|
| `packages/glam/src/<m>.cairo` | `intvec.py`: `consts`, `methods`, `operators`, `HELPERS` |
| `packages/glam/tests/test_<m>.cairo` | `intvec_tests.py` (expected values computed with Python integers) |
| `packages/benches/tests/bench_<m>.cairo` | `intvec_bench.py`: `lib_benches`, `alt_benches` |
| `packages/benches/src/alt/<m>.cairo` | `intvec_bench.py`: `alts`, `ALT_HELPERS` |

Never edit a generated file: change the template, regenerate, then refresh the snapshots
(`scripts/bench.py snapshot bench_<m>` for the six modules).

How the template is organised:

- `Ty` describes one type (signedness, dimension, names); `t.cw(f)` builds the component-wise
  struct literal, which is what almost every method body is.
- `methods(t)` is the single list behind both the trait declaration (docs with the `Mirrors` /
  `#### Panics` / `#### Deviations` template) and the impl.
- Scalar kernels (`abs_diff_i32`, `div_euclid_i32`, `wrapping_mul_i32`, ...) are private functions
  of each module, emitted only when referenced (`used_helpers`).
- A formulation choice is data: `is_fused(t, op)` picks, per type, between the literal glam-rs
  expression and the `felt252`-fused kernel; the generator emits the other one in
  `benches::alt::<m>` with its bench, so every choice stays measurable. The scalar-level
  experiments (sign tests, euclidean division, casts, shifts ...) are emitted for the 3D types only.

## Compile budget of the generated tests

The Cairo compiler pays per call site: an `assert_eq!` inlines the operator under test and a
formatting path. The first version of `intvec_tests.py` unrolled every case (12 300 assertions in
six files, 30 000 lines): `scarb build --test -p glam` took 81 s and about 32 GB, and the GitHub
runner was killed while compiling the `glam_tests` crate. The template now emits, per function
group, one `const NAME: [[i64; W]; K]` table (Python-computed expectations, one row per case,
readers `vc`, `vo`, `bv`, `opt`, ... in the file prelude) and ONE looping `#[test]`; the cost is
the number of checks, not cases x checks. Rules for new tests: add a row, not an assertion; keep a
`#[should_panic]` per panic path; at most 6 fuzz properties per module; measure with
`scarb clean && /usr/bin/time -l scarb build --test -p glam`.
