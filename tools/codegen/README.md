# tools/codegen

Generators for the modules of `glam` that glam-rs itself generates from one template.

## intvec.py - IVec2/3/4 and UVec2/3/4

```
tools/codegen/intvec.py            # regenerate, then `scarb fmt` the workspace
tools/codegen/intvec.py --check    # exit 1 if a committed file differs from the generator output
tools/codegen/intvec.py --only src,tests,bench,alt
```

Dependency-free (python >= 3.8, `scarb` on the `PATH` for the formatting pass). For each of the
six types it writes four files, all starting with `// GENERATED by tools/codegen/intvec.py`:

| output | template |
|---|---|
| `packages/glam/src/<m>.cairo` | `intvec.py`: `consts`, `methods`, `operators`, `HELPERS` |
| `packages/glam/tests/test_<m>.cairo` | `intvec_tests.py` (expected values computed with Python integers) |
| `packages/benches/tests/bench_<m>.cairo` | `intvec_bench.py`: `lib_benches`, `alt_benches` |
| `packages/benches/src/alt/<m>.cairo` | `intvec_bench.py`: `alts`, `ALT_HELPERS` |

Never edit a generated file: change the template, regenerate, then refresh the snapshots
(`scripts/bench.py snapshot bench_<m>` for the six modules).

How the template is organised:

- `Ty` describes one type (signedness, dimension, names); `t.cw(f)` builds the component-wise
  struct literal, which is what almost every method body is.
- `methods(t)` is the single list behind both the trait declaration (docs with the `Mirrors` /
  `#### Panics` / `#### Deviations` template) and the impl.
- Scalar kernels (`abs_diff_i32`, `div_euclid_i32`, `wrapping_mul_i32`, ...) are private functions
  of each module, emitted only when referenced (`used_helpers`).
- A formulation choice is data: `is_fused(t, op)` picks, per type, between the literal glam-rs
  expression and the `felt252`-fused kernel; the generator emits the other one in
  `benches::alt::<m>` with its bench, so every choice stays measurable. The scalar-level
  experiments (sign tests, euclidean division, casts, shifts ...) are emitted for the 3D types only.

## fvec.py - Vec2/Vec3/Vec4 (the Q32.32 vectors)

```
tools/codegen/fvec.py            # regenerate, then `scarb fmt` the workspace
tools/codegen/fvec.py --check    # exit 1 if a committed file differs from the generator output
tools/codegen/fvec.py --only src,tests,bench,alt
```

Same shape as `intvec.py` (same four outputs per type, same `--check` contract), for the three
fixed-point vectors. Files start with `// GENERATED by tools/codegen/fvec.py`.

| output | template |
|---|---|
| `packages/glam/src/<m>.cairo` | `fvec.py`: `consts`, `methods`, `operators`, `HELPERS` |
| `packages/glam/tests/test_<m>.cairo` | `fvec_tests.py` (expected values from the Q32.32 Python oracle of its `RAW SEMANTICS` section) |
| `packages/benches/tests/bench_<m>.cairo` | `fvec.py`: `lib_benches`, `alt_benches` |
| `packages/benches/src/alt/<m>.cairo` | `fvec.py`: `alts` |

What differs from the integer generator:

- every product goes through a fused kernel of `fixed::wide` (`dot{n}`, `mul_sub`, `mul_add`,
  `norm{n}`, `distance{n}`, the shared `Norm` / `Recip`): one rescale per output scalar. The
  kernel names are built from the dimension (`dot_call`, `norm_call`, `distance_call`), so the
  numerics are templated too, not just the component-wise plumbing;
- `FUSED_BODIES` holds both formulations of every measured choice (library and `benches::alt`),
  `is_fused(t, op)` picks the winner and `ALT_NAMES` names the loser. Adding a candidate means
  adding a body function, an entry in `sigs` / `notes` / `ALT_NAMES` and a line in `fused_ops`:
  the bench pair and the `alt` function are then emitted automatically;
- the dimension-specific numerics (`cross`, `perp` / `perp_dot` / `rotate`, `any_orthonormal_*`)
  are per-type snippets guarded by `if n == ...` in `methods`, never `if n` inside a body;
- the bench file declares its operands as `const`s (`A`, `B`, `UNIT`, `K_HALF`, ...) instead of
  inlining `Vec3Trait::new(FixedTrait::from_raw(..), ..)` at every call site: the inline form
  wraps over three lines per input and made the file 2.6x longer;
- `fvec_tests.py` carries a small Q32.32 oracle in Python (floor rescale, truncated division,
  the round-to-nearest shared reciprocal, integer square root) so the tables pin the bit-exact
  fixed-point semantics. Parity with glam-rs itself is the job of `tools/refgen`
  (`tests/golden_<m>.cairo`), which uses `DVec*` as the oracle.

## Compile budget of the generated tests

The Cairo compiler pays per call site: an `assert_eq!` inlines the operator under test and a
formatting path. The first version of `intvec_tests.py` unrolled every case (12 300 assertions in
six files, 30 000 lines): `scarb build --test -p glam` took 81 s and about 32 GB, and the GitHub
runner was killed while compiling the `glam_tests` crate. The template now emits, per function
group, one `const NAME: [[i64; W]; K]` table (Python-computed expectations, one row per case,
readers `vc`, `vo`, `bv`, `opt`, ... in the file prelude) and ONE looping `#[test]`; the cost is
the number of checks, not cases x checks. Rules for new tests: add a row, not an assertion; keep a
`#[should_panic]` per panic path; at most 6 fuzz properties per module; measure with
`scarb clean && /usr/bin/time -l scarb build --test -p glam`.


Measured on the merged state of this repository (`scarb clean && /usr/bin/time -l scarb build
--test -p glam`): 5.0 GB and 20 s without the three fixed-point vector modules, 7.9 GB and 19 s
with them (test files of ~1 000 lines each plus golden files of ~1 300). The three `Vec*` test
files and their golden vectors are the budget for one wave of modules: the next ones must stay at
that size, which is what the table-per-group rule and the per-module caps (<= 1 200 lines of
tests, <= 1 500 lines of golden vectors, <= 6 fuzz properties at `runs: 128`) are for.

## swizzles.py - `Vec2/3/4Swizzles` for the nine vector types

```
tools/codegen/swizzles.py                  # regenerate, then `scarb fmt` the workspace
tools/codegen/swizzles.py --check          # exit 1 if a committed file differs from the generator output
tools/codegen/swizzles.py --glam-src DIR   # also compare the method lists with glam-rs `src/swizzles`
```

`DIR` is the `src/swizzles` directory of a glam-rs 0.33.8 checkout: the generator then verifies that
each trait has exactly the methods of `vec_traits.rs`, in the same order (28 / 123 / 372: the
identity, every permutation with repetition of length 2 to 4, and the `with_*` setters of the
distinct components of length `k < n`). Files start with `// GENERATED by tools/codegen/swizzles.py`.

| output | content |
|---|---|
| `packages/glam/src/swizzles.cairo` | the nine submodules and the re-exports (`glam::swizzles::Vec3Swizzles`) |
| `packages/glam/src/swizzles/<m>.cairo` | one `pub trait <T>Swizzles` + `pub impl <T>SwizzlesImpl` per type (`<m>` = `vec2` .. `uvec4`), every method `#[inline(always)]` |
| `packages/glam/tests/test_swizzles.cairo` | per type ONE test over the methods, plus `anchors` and `checker_detects_mismatch` per scalar family |
| `packages/benches/tests/bench_swizzles.cairo` | `BENCH_METHODS`: 3 to 6 representative methods per type |

- glam-rs implements one trait (`Vec3Swizzles`) for `Vec3`, `DVec3`, `IVec3`, ... with associated
  `Vec2` / `Vec4` types. A Cairo trait cannot do that here, so there is one trait per type
  (`Vec3Swizzles`, `IVec3Swizzles`, `UVec3Swizzles`). One trait per type (372 methods for `Vec4`)
  compiles fast enough that no split by return type was needed (see the numbers below).
- The tests decode an expected result from a digit code: digit `d` in 1..4 is component `d - 1` of
  `self`, digit 5..7 is component `d - 5` of the `rhs` of a `with_*` setter (`xxyz` = `1123`,
  `with_wzy` = `1765`). The three scalar families have their own module (`val` differs).
  `sampled()` decides what is tested: everything, except the 256 `Vec4`-returning swizzles of a
  `Vec4`, of which the 24 permutations of `xyzw` and the `aabb` / `abab` shapes (52 per type) are
  tested. The exhaustive version of the same tests was measured (below): it only breaks the
  1 200 lines cap of a test file.
- A swizzle is a struct construction: the gas of a method is 100 per scalar built and nothing else,
  so `bench_swizzles` carries a few methods per type, not 500.

Measured on this repository (`scarb clean` first, `/usr/bin/time -l`):

| | main (stub) | 9 traits, 1 trait per type | + exhaustive tests |
|---|---|---|---|
| `scarb build -p glam` | 1.2 s, 0.97 GB | 1.3 s, 1.15 GB | |
| `scarb build --test -p glam` | 13.2 s, 7.75 GB | 14.2 s, 8.16 GB | 13.7 s, 8.04 GB (1 742 lines) |
